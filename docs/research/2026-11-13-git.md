# Git: how VS Code and Zed do it

Research for phase 5 (Git for viewing only). Sources read:
- VS Code: `microsoft/vscode` branch `main`, read on 2026-11-13, MIT license. Covers `extensions/git/` and `src/vs/workbench/contrib/scm/`.
- Zed: revision `b5cd310`, which Lucerna pins, GPL license. Only the design is studied, no code is copied. Crates read: `git`, `buffer_diff`, `git_ui`, `project/src/git_store*`, `editor`, `project_panel`.

The spec that uses these results: `docs/superpowers/specs/2026-11-13-git-view-design.md`.

## 1. Reading git: a library or the `git` command

**Zed** does not use a library. Every operation calls the `git` command:
- Status: `git status --porcelain=v1 --untracked-files=all --no-renames -z -- <paths>`. A list of paths can be passed to refresh only part of the tree.
- File contents at HEAD (`HEAD:<path>`) and in the index (`:<path>`) are read through **one** long-lived `git cat-file --batch` process.
- Added and removed line counts come from `git diff --numstat`.
- Every command carries `-c core.fsmonitor=false --no-optional-locks --no-pager`. In an untrusted directory, Zed also disables hooks, `credential.helper` and `diff.external`.
- Each repo has a work queue that runs sequentially on a background thread. A new job with the same key replaces the older job waiting in the queue. For example, a "rescan everything" has at most one job waiting.

**VS Code** also calls the `git` command, through the git extension written in TypeScript.

**Lucerna measured on this machine (macOS, Apple Silicon).** The test programs are release builds, stripped. The test repo is Zed at the revision above, 4,401 tracked files:

| Approach | Extra binary size | Repo status, clean | Status, 20 modified files + 1,000 new files | `cargo deny` |
|---|---|---|---|---|
| `gix` 0.90 (`status`, `sha1`, `parallel`) | +3.3 MB, ~440 crates | 55–120 ms | ~60 ms | pass |
| `git2` 0.21 (`vendored-libgit2`) | +0.8 MB, links to the system libz and libiconv | 85–195 ms | 105–135 ms | pass |
| `git` 2.x command | 0 | 100–110 ms (first run 750 ms from a cold cache) | ~100 ms | not applicable |

A few more measurements:
- The release `luc` binary is currently 48.5 MB.
- A line diff of the file `editor.rs` (13,446 lines) with `similar` takes about 6 ms. `similar` is already in the workspace, used by `lucerna-text`.
- The Lucerna repo (503 files): `gix` 5–16 ms, `git2` about 10 ms, `git` command 24 ms.

**Lucerna chooses the `git` command, like Zed.** Reasons:
- The binary does not grow.
- Results always match the git the agent is using: worktrees whose `.git` file points elsewhere, sparse checkout, LFS, `core.autocrlf`, the user's own config.
- Speed on par with `git2`.

The price is that the machine needs git. On macOS, `/usr/bin/git` is a shim: if the Command Line Tools are not installed, it pops up a dialog asking to install them. So Lucerna finds git through the login shell's PATH (`lucerna-lsp::env::which`) and does not call `/usr/bin/git` directly without checking first.

## 2. The comparison base (diff base)

| | VS Code | Zed |
|---|---|---|
| Gutter compares against | the index (the staged version). A staged file gets an extra HEAD↔index layer, in a lighter color | HEAD↔buffer (an "uncommitted" diff), the extra layer is the index |
| Setting to change the base | none | `git.diff_base`: `"head"` (default) or `"default_branch"`. The gutter, the project panel colors and `git::Diff` all change with it |
| Branch-based view | none built in | `git::DiffBranch` opens a "Changes since main" tab. The diff goes from the merge-base with the default branch to the version on disk; a branch picker in the toolbar changes the base in place |
| Finding the default branch | not applicable | `refs/remotes/upstream/HEAD`, then `refs/remotes/origin/HEAD`, … |

Lucerna follows Zed: a `git.diffBase` setting with default `"head"`, an Uncommitted Changes tab and a Changes since main tab. Users let the agent commit by itself, so a branch-based tab is needed to review the whole task.

## 3. Gutter

| | VS Code | Zed |
|---|---|---|
| Bar | 3 px (`scm.diffDecorationsGutterWidth` from 1 to 5), between the line numbers and the text. A modified line is drawn with diagonal stripes | `floor(0.275 × line_height)` wide, at the left edge of the gutter, square corners |
| Deleted lines | a 4×8 px triangle at the bottom of the line above | a pill one line tall, sitting between two lines, with half of it clipped |
| Color | `editorGutter.{added,modified,deleted}Background` | `version_control.{added,modified,deleted}`, blended onto `editor.background` |
| Clicking the bar | opens a peek frame containing an inline diff, with Stage, Revert, Next, Prev | expands the hunk right in the editor (deleted lines become real lines, read-only) |
| Go to a change | `workbench.action.editor.nextChange` / `previousChange`: Alt+F5 / Shift+Alt+F5. `editor.action.dirtydiff.next` / `previous`: Alt+F3 (opens the peek) | `editor::GoToHunk` / `GoToPreviousHunk`: Cmd+F8 / Cmd+Shift+F8. Vim: `]c` / `[c` |
| Recompute | throttle 200 ms, capped at 1 s | re-diffs the whole file in a background task after every edit, not incrementally. No debounce by default; if enabled, at least 50 ms |
| Algorithm | VS Code's "advanced" | imara-diff Histogram, plus git's indent heuristic |
| Settings | `scm.diffDecorations` (`all`, `gutter`, `overview`, `minimap`, `none`), `…GutterVisibility`, `…GutterAction` | `git.git_gutter` (`tracked_files`, `hide`), `git.gutter_debounce`, `git.hunk_style` |

Lucerna takes the look from Zed (position, width, the delete mark), and the keys and settings from VS Code. `]c` and `[c` are added when Vim is on.

## 4. Explorer and project panel

| | VS Code | Zed |
|---|---|---|
| Coloring file names | yes (`explorer.decorations.colors`) | yes (`project_panel.git_status`) |
| Letters | yes, on by default (`explorer.decorations.badges`): M, A, D, R, C, T, U (untracked), !, S | yes but off by default (`git_status_indicator`): !, U, D, M, A |
| Folders | take the color of a child, plus a dim dot. Priority: conflict > ignored > modified > the rest. A deleted file does not propagate upward | the most important child's color (aggregated over the tree). Priority: conflict > deleted > modified > created > ignored |
| Color keys | `gitDecoration.*ResourceForeground` | `conflict`, `deleted`, `modified`, `created`, `ignored` (a different set from `version_control.*`) |

Lucerna colors file and folder names like Zed, does not show letters (Zed's default), and uses VS Code's setting keys.

## 5. A view that gathers all changes

- **VS Code**: the command `git.viewChanges` opens a multi-diff editor. It is one tab made of several stacked diff editors, each file having a collapsible header and an Open File button. An empty group shows a toast-style message.
- **Zed**: the command `git::Diff` opens an "Uncommitted Changes" tab. It is a multibuffer containing every changed file:
  - every hunk is expanded by default, with 2 lines of context (`excerpt_context_lines`);
  - file order: conflicts, then tracked files, then new files; deleted files are collapsed by default;
  - when the status changes the file list is rebuilt, when one file's diff changes only that file is rebuilt;
  - loads at most 16 files at a time;
  - the empty state is the text "No uncommitted changes" in the center.

  The toolbar has previous/next hunk, Stage, Commit and a one-column/two-column toggle. This view is editable.

Lucerna builds this view on an excerpt list, read-only, following Zed's layout and dropping the stage and commit parts.

## 6. Diff of a single file

- **VS Code**: `git.openChange` ("Open Changes"):
  - a modified file: compares the index (or HEAD) with the file on disk;
  - a staged file: compares HEAD with the index;
  - a new file: opens the plain file;
  - a deleted file: opens the HEAD version, read-only.

  The diff editor defaults to two columns, switching to one column when the editor is narrower than 900 px. By default it ignores leading and trailing whitespace on a line.
- **Zed**: `git::OpenFileDiff` opens a `SoloDiffView`, showing the whole file by default. There is a two-column form (`SplittableEditor`), on by default, switching to one column when narrower than 100 em.

Lucerna's first version has only one column. The two-column form is left for a later version.

## 7. Refreshing

- **Zed**: watcher latency 100 ms.
  - A file in the worktree changes: run `git status -- <paths>` for just those paths, then patch into the tree.
  - A file in `.git` changes (`index`, `HEAD`, `refs/…`): rescan everything.
  - Ignores `objects`, `hooks`, `lfs`, `rebase-*`, `sequencer`, `fsmonitor--daemon`, `COMMIT_EDITMSG`, `FETCH_HEAD`, `ORIG_HEAD`, `gc.pid`.
  - No limit on the number of entries and no limit on file size.
- **VS Code**: 1 s debounce, waits for git to be idle **and** the window to be focused, runs `git status -z -uall`, then holds for 5 s.
  - `git.statusLimit` defaults to 10,000. Above the threshold the repo is considered "too large": automatic refresh stops and one notice is shown.
  - File size limit for diffs: 50 MB (`diffEditor.maxFileSize`).

Lucerna refreshes fast like Zed because users want to see changes immediately when the agent writes a file, and takes VS Code's `git.statusLimit` threshold to protect very large repos.

## 8. Restricted Mode

- **VS Code**: the git extension does not run in an untrusted workspace.
- **Zed**: still runs git, but disables hooks, the credential helper and external diff.

A repo's local config (`core.fsmonitor`, `filter.*.clean`, `diff.*.textconv`) can run arbitrary commands even when only reading status. So Lucerna follows VS Code: do not run git in an untrusted directory.

## 9. Lucerna measurements (5.1)

Measured with the headless benchmark `crates/lucerna-workbench/tests/git_perf.rs` (`#[ignore]`, set `LUCERNA_GIT_BENCH_REPO`). It runs a real `GitStore` in a `TestAppContext` with real `git`, timed with `std::time::Instant`. Repo: Zed at the pinned revision (4,401 files, `crates/editor/src/editor.rs` is 13,446 lines long); the commit step runs on a temporary branch `lucerna-bench` in the clone, then the clone is deleted. Machine: macOS, **debug** build (not optimized), so real release numbers can only be better. One run, not averaged.

| Threshold (spec §5) | Measured | Result |
|---|---|---|
| Explorer colors shown ≤ 500 ms after the scan finishes (first rescan → first snapshot) | 321 ms | met |
| 1 file changed → snapshot updated ≤ 300 ms (`paths_changed`, 1 file) | 49 ms | met (excludes watcher latency) |
| 500 files written at once: refresh work coalesces, at most one job waiting | 2 status jobs (including the running one), settled after 432 ms, including the time to write 500 files | met |
| Commit → update ≤ 1 s (commit, `rescan` → snapshot) | 276 ms | met |
| Gutter diff of a 13,446-line file ≤ 20 ms on the background thread | 104 ms total, including reading the blob via `git cat-file` and the diff, the 50 ms debounce sits on the fake clock | the diff part is not separated out; see the note |

Note on the last row: 104 ms is the whole chain (spawning `git`, reading the blob, diff, publish) in a debug build, not the diff alone. The diff runs on a background thread, so it does not block the UI thread. There is no separate number for `diff_hunks` in a release build, so the 20 ms item is not confirmed by a direct measurement.

**Not measured:**
- Dropped frames while 500 files are written: needs running the real UI and watching the frame-time log. The benchmark measures only the job count and settle time. The refresh runs on a background thread and coalesces, so the UI thread is not blocked, but it has not been observed by eye.
- Watcher latency (from the file write to the event): not part of the headless benchmark; the numbers above start from the moment `paths_changed` is called.
- Binary size: no release build, because the `target/` folder is shared with other sessions running cargo. Reasoning: compared with `7db69cb`, `Cargo.lock` only adds the crate `lucerna-git`; its external dependencies (`similar`, `notify`, `crossbeam-channel`, `tracing`) are already in the workspace, so the binary grows by exactly the code of `lucerna-git`. Not measured.

Addition to 5.1: a separate benchmark for `lucerna-git`'s diff (excluding spawning `git`) with 10,000 lines measured 7.79 ms in a debug build, within the 20 ms threshold. The 104 ms figure above is the whole chain (spawn `git`, read the blob, diff, publish).

## 10. Lucerna measurements (5.2)

The same benchmark `crates/lucerna-workbench/tests/git_perf.rs` (`#[ignore]`, `LUCERNA_GIT_BENCH_REPO`), with two more tests: `diff_tab_200_files` and `file_tab_reload`. All three tests refuse to run if the repo's `git status --porcelain` is not empty (to avoid damaging a real repo). Repo: a temporary clone of Zed at the pinned revision (4,401 files), deleted after measuring. Machine macOS, **debug** build; two runs gave nearly identical numbers.

**Method note.** The tests run in `TestAppContext`, where the background executor runs jobs one at a time on a single thread, so the real app's 16 parallel file loads become sequential. Every hunk-loading number below is an upper bound. Time is taken with `Instant` (real clock); the 60 ms debounce goes through the fake clock.

| Threshold (spec §5) | Measured | Result |
|---|---|---|
| Uncommitted Changes tab, 200 changed files: header shown ≤ 200 ms (from `git.viewChanges` until all 200 files are listed) | 70-73 ms | met |
| Hunks of the files in the viewport ≤ 500 ms (first 10 files, about one window) | 348 ms (sequential, debug) | met, an upper bound |
| All hunks of all 200 files | 2.97 s sequential (first 30 files: 705 ms) | no threshold; ~15 ms per file in a debug build, the app loads up to 16 files in parallel |
| One tab paint after loading finishes | 9 ms | no threshold |
| File tab (whole file) of 13,446 lines, one edit then a reload after the debounce | 89-90 ms total, sequential (including the background diff, publishing into the list; the longest few jobs 22 ms, 8 ms and 60 ms) | no threshold of its own |
| The UI-thread part around that reload | typing one character (`type_text`) 11 ms, repaint after the reload 8 ms | no threshold of its own |
| Opening a 13,446-line file tab the first time (from `open_file_diff` until all work finishes, buffer already open) | 246 ms (before the fix: ~3.8 s) | no threshold of its own |

**Re-measured after the fix (end-of-branch review).** The ~3.8 s when opening a file tab was not from opening the buffer (the clock starts after the buffer is open) but from the background coloring work: cutting spans by line is O(lines × spans), with every line walking all the spans of the whole excerpt, and a file tab is one excerpt as long as the whole file. Now each span walks only the lines it covers (finding the first line by binary search), so it is linear. Same repo, same debug build, two runs: open → done 246.7 ms and 246.2 ms; first paint 6.7-6.8 ms; typing one character 8.4-8.5 ms; edit → reload done 87.2-87.9 ms total sequential (longest jobs 55 ms, 21 ms, 7 ms); repaint after reload 3.6-3.8 ms. Each frame also no longer looks up the selected line for every visible line, and does not rescan every line of the file to find uncolored lines when the file and colors have not changed.

**Not measured, and why:**
- Separating the UI-thread part from the background part of the file-tab reload: the test executor does not say which job belongs to which thread, so there is only the total and the list of long jobs. The 90 ms sequential total is an upper bound for the background part; the UI part is certainly smaller.
- The first file-tab open in a release build; the debug build is now 246 ms (see above).
- A release build and real parallelism (16 jobs) for the 200-file tab; worth re-measuring when a release build exists.
- No by-eye comparison with Zed yet (see spec §2).
