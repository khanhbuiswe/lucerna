# Research: hot exit (keeping unsaved content across an app quit)

Date 2026-11-16. Research for Lucerna keeping unsaved editor content when quitting and restoring it on the next launch. Extends §8.6 of `2026-11-15-multi-window.md`.

Sources:

## 1. VS Code: the `files.hotExit` setting

Declared in `workbench/contrib/files/browser/files.contribution.ts:134-156`, constants in `platform/files/common/files.ts:1535-1538`. Scope `APPLICATION` (read only from user settings).

| Value | Desktop | Web |
|---|---|---|
| `off` | Hot exit off. Closing a window or quitting both ask to save. | yes |
| `onExit` | **Default on desktop.** Hot exit when quitting the app (`workbench.action.quit`: Cmd+Q, menu, command palette) and when closing the last window on Windows/Linux. | not available |
| `onExitAndWindowClose` | Like `onExit`, plus when closing **any** window that has a folder/workspace, even if it is not the last window. | **default on web** |

`isHotExitEnabled` returns false for "transient" workspaces because they are not restored (`workbench/services/filesConfiguration/common/filesConfigurationService.ts:534-542`).

### 1.1 Backup decision by shutdown reason (`shouldBackupBeforeShutdown`, desktop tracker `:189-236`)

- Hot exit off → no backup, ask to save.
- Extension development window → always back up, no prompt.
- `ShutdownReason.QUIT` (quitting the app) → back up **every** dirty working copy (`:217-218`).
- `ShutdownReason.RELOAD` (Reload Window) → back up everything (`:221-222`).
- `ShutdownReason.CLOSE` (closing one window):
  - `onExitAndWindowClose` and the window has a folder/workspace → back up everything (`:202-204`).
  - macOS, or more than one window left (the app does not quit after this window closes): a window with a folder only backs up *scratchpads* automatically and asks to save the rest; an empty window asks for everything (`:206-212`).
  - Last window on Windows/Linux → back up everything, because the app quits right after (`:214`).
- `ShutdownReason.LOAD` (changing workspace in the same window): has a folder + `onExitAndWindowClose` → back up all; has a folder + `onExit` → only scratchpads; empty window → no backup (`:225-234`).

Consequence on macOS with the default `onExit`: Cmd+Q **asks nothing**; closing a window with Cmd+W/the red button (even the last window, because the app keeps running) **does ask**.

### 1.2 Auto save comes before hot exit

If `files.autoSave` is not `off`, at shutdown VS Code **actually saves** the files that can be auto saved (skipping save participants, `skipSaveParticipants: true`), and only then considers a backup for the rest (untitled, or files that failed to save) (desktop tracker `:112-138`, `:357-386`).

## 2. VS Code: when backups are written and deleted

### 2.1 Written continuously while typing (not only at quit)

The common tracker listens to `onDidChangeContent`, `onDidChangeDirty`, `onDidRegister`, `onDidUnregister` of every working copy (`:50-64`).

- Each content change: bumps a "content version" of the working copy (`:148-152`), then `scheduleBackup` (`:160-166`).
- `scheduleBackup` cancels the previous schedule and sets a new `setTimeout`, so this is a **debounce**: the backup runs after the user stops typing for a while (`:169-223`).
- Constant `DEFAULT_BACKUP_SCHEDULE_DELAYS` (`:91-94`): **`default` = 1000 ms**, **`delayed` = 2000 ms**. `delayed` is used when the file has auto save with a short delay (`hasShortAutoSaveDelay`), to avoid a race between auto save (default 1 s) and the backup. Untitled always uses `default` (`:225-238`). A working copy can set its own `backupDelay`.
- When the timer fires: ask the working copy for `backup(token)` to get content + metadata, then `workingCopyBackupService.backup(wc, content, contentVersion, meta)` (`:179-209`).

**Crash safety:** yes, at the level of "lose at most ~1 s of the last typing". The backup is already on disk while the app runs, so a crash or kill still leaves it. Writes are atomic: write `<backup>.vsctmp` and then `move` over it (atomic rename) if the file system supports `FileAtomicRename` (backup service `:314-329`; the suffix `WORKING_COPY_BACKUP_TEMP_FILE_SUFFIX = '.vsctmp'` is in `platform/backup/common/backup.ts:9`). `.vsctmp` files are ignored when reading (`:60`) and when checking whether a folder has backups (`platform/backup/electron-main/backupMainService.ts:347`). Every write/delete on a backup goes through a per-resource queue (`ResourceQueue`, backup service `:232`) to keep write-then-delete ordering.

The backup service remembers in RAM the `(versionId, meta)` of the last backup for each resource; `backup()` is skipped if a backup with the same version and meta already exists (`:90-105`, `:277-292`). So at quit, a working copy that was already backed up with the latest version does not need to be written again.

### 2.2 Deleting backups

- **Save or revert** → the working copy is no longer dirty → `onDidChangeDirty` calls `discardBackup` immediately, no debounce (common tracker `:135-146`, `:244-263`).
- **Closing an editor without saving**: the "Don't Save" dialog reverts the model → no longer dirty → backup deleted. When the model is disposed (unregistered) the backup is deleted too (`:120-133`).
- **At shutdown, nothing is dirty**: delete every backup of the window, *except* backups not yet restored in this session if the window has a folder; an empty window also deletes the unrestored ones, so empty windows do not resurrect forever (desktop tracker `:404-424`). Never deletes before the old backup list has been fully read (`isReady`, `:443-450`).
- **At startup**: a backup folder of a workspace/folder/empty window that has no backup files left is moved away (`deleteStaleBackup`, `backupMainService.ts:260-266`).
- After the tracker receives `onWillShutdown` (shutdown is certain), it cancels every scheduled backup and "suspends" itself so that a backup is not written half-way when the process is terminated (common tracker `:68-79`; desktop tracker `:77-110`, issue #138055).

## 3. VS Code: where it is stored and the format

### 3.1 Folder layout

```
<userData>/Backups/                         (environmentMainService.ts:49 → join(userDataPath, 'Backups'))
  <workspace id>/                           .code-workspace workspace: the workspace id
  <md5(folder path)>/                       single folder: md5 of fsPath, lowercased except on Linux (backupMainService.ts:404-415)
  <empty window id>/                        empty window: a random id (createEmptyWorkspaceIdentifier)
    file/<hash>                             one backup file per working copy
    untitled/<hash>
    <other scheme>/<hash>
```

- `toBackupResource` = `joinPath(backupHome, resource.scheme, hashIdentifier(identifier))` (backup service `:565-567`).
- `hashIdentifier`: hashes the `fsPath` (for `file` and `untitled`) or the URI string with VS Code's numeric `hash()` function, printed in base 16; if there is a `typeId`, the typeId's hash is joined into the path before hashing (`:645-675`).
- The list of workspaces/folders/empty windows that have backups is stored in the state service (`storage.json`) under the key `backupWorkspaces` = `{ workspaces: [{id, configURIPath}], folders: [{folderUri}], emptyWindows: [{backupFolder}] }` (`backupMainService.ts:28`, `:362-402`; types in `platform/backup/node/backup.ts:19-75`).

### 3.2 Backup file format

A header line and then the content:

```
<resource URI> <JSON meta with typeId added>\n<content, UTF-8>
```

- `createPreamble` = `resource.toString()` + a space + `JSON.stringify({...meta, typeId})` + `\n` (backup service `:341-343`). The space was chosen because it is always escaped in URIs.
- `PREAMBLE_MAX_LENGTH = 10000`: if the header is longer, the meta is dropped and only the URI is kept (`:228`, `:298-301`).
- Text file meta (`IBackupMetaData`, text model `:45-51`): `mtime`, `ctime`, `size`, `etag` (from the last read/save of the file on disk) and `orphaned` (the file had been deleted when backed up). **The encoding is not stored**: backup content is always UTF-8 (`:243-246`); on restore, the encoding is taken again from the file's settings/preferences (`:478-482`).
- Reading: take the first chunk, look for `\n`; if none, treat the backup as corrupt and skip it (`:505-510`).

## 4. VS Code: restore

### 4.1 Which windows are reopened

On the first startup of the main process (`windowsMainService.ts:415-426`):
- **Empty windows with backups are always reopened**, regardless of `window.restoreWindows` (`:422-423`). Untitled workspaces too (`:418-420`).
- **Windows with a folder/workspace that have backups are not forced to reopen.** They only open if `window.restoreWindows` (default `all`) opens them (`:1095-1130`). The comment in the desktop tracker `:418-421` says it plainly: VS Code does not reopen a folder window because it has backups; unrestored backups are kept so the next time that folder is opened they are restored. The setting's description says the list of windows with unsaved files is under *File > Open Recent > More...* (`getDirtyWorkspaces`, `backupMainService.ts:299-317`).
- A folder/workspace with backups whose **folder no longer exists on disk** → the backup folder is renamed to be the backup of an empty window, so on that startup it opens as an empty window (`backupMainService.ts:159-228`, `:283-297`).
- With `onExitAndWindowClose`, `getWorkspaceBackups`/`getFolderBackups` return empty: only windows without a folder are restored at startup (`:69-87`).

### 4.2 How a backup becomes a dirty model

1. After `LifecyclePhase.Restored`, the tracker reads the backup list (`getBackups`, reading each file's header) into `unrestoredBackups` (common tracker `:343-354`).
2. When an editor handler registers (for example for text files), each backup is handed to it: if an editor is already open for it (from saved editor state), that editor is used; if not, a new **pinned, inactive, preserveFocus** editor is opened (`:356-410`). Then the non-visible editors are `resolve()`d so the models get loaded (`:416-422`).
3. On the first resolve, the text model **prefers the backup over the file on disk** (`doResolve`, text model `:321-339`). `doResolveFromBackup` builds the model from the backup content, sets `lastResolvedFileStat` to the `mtime/ctime/size/etag` **in the backup's meta** (without stat-ing the disk), marks it dirty, and restores the `orphaned` flag if the meta says so (`:503-525`). No meta → `etag = ETAG_DISABLED` (no conflict check will be done).
4. Undo history is not restored; the new model has only the content.

### 4.3 The file on disk changes or is deleted while the app is off

- On restore **there is no disk check** at all: the user sees a dirty tab with their content, no notification.
- **File changed**: detected on **save**. `validateWriteFile` (`platform/files/common/fileService.ts:502-537`) compares the expected `mtime` and `etag` (from the backup meta) with the current stat: if the on-disk `mtime` is newer and the etag (computed from mtime + size) differs, it tries reading the file; identical content allows the write, different content throws `FILE_MODIFIED_SINCE`. The save error handler shows the notification *"Failed to save '…': The content of the file is newer. Please compare your version with the file contents or overwrite…"* with two buttons **Compare** (opens the "Resolve save conflict" diff) and **Overwrite** (save skipping the check) (`workbench/contrib/files/browser/editors/textFileSaveErrorHandler.ts:113-135`, `:238-258`, `:387`). This is a notification, not a modal.
- **File deleted**: the model is not marked orphaned (only the runtime watcher does that, text model `:158-201`), unless the file had been deleted before the backup (`orphaned: true` in the meta). On save, `validateWriteFile` fails to stat → writes normally, i.e. **the file is silently recreated** (`fileService.ts:487-492`).

## 5. VS Code: the quit flow

- macOS Cmd+Q / the Quit menu / Dock Quit / Log Out all go through Electron `before-quit` → `app.quit()` closes each window; each window unloads with reason QUIT and can veto (`platform/lifecycle/electron-main/lifecycleMainService.ts:277-298`, `:421-476`, `:641-667`). Only when no window vetoes does it reach `will-quit`. (Electron emits `before-quit` when macOS sends terminate, so Dock Quit/logout also get a chance to veto; on Windows shutdown/logout does not emit it.)
- With `onExit` and **every working copy backed up successfully** → no veto, **no prompt** (desktop tracker `:145-154`). If a backup already exists for the current version it is not rewritten (`:290-293`), so quitting is nearly instant.
- **Slow backup**: runs in `withProgressAndCancellation` with `delay: 800` ms; past 800 ms a progress dialog *"Backing up editors with unsaved changes is taking a bit longer..."* appears with a Cancel button (`:279-319`, `:474-484`). Clicking Cancel → the working copies not yet backed up fall back to the normal save prompt (Save / Don't Save / Cancel, `:321-355`).
- **Backup failure** (for example disk full) → an error dialog *"The following editors with unsaved changes could not be saved to the backup location."* with buttons **OK** (veto, cancel the quit) and **Quit Anyway** / **Close Anyway** / **Reload Anyway** (`:162-171`, `:238-277`). An extension development window does not block.
- **Large files**: no separate size limit for backups is visible in the tracker or the backup service; a large file only makes the backup slow, falling into the "taking a bit longer" path above.
- An unattended restart (auto update) is blocked if hot exit is off, an auto save is pending, or a backup has not caught up with the latest version (`:54-75`).

## 6. Zed

### 6.1 Where and what is stored

- In the shared SQLite `<data_dir>/db/<scope>/db.sqlite` (`crates/paths/src/paths.rs:260`, `crates/db/src/db.rs:138`), the `editors` table of `EditorDb` (`crates/editor/src/persistence.rs:132-200`). Key `(item_id, workspace_id)`. Relevant columns: `path`/`buffer_path` (absolute path, may be NULL for a buffer without a file), `contents TEXT` (the whole text, only when dirty), `language TEXT`, `mtime_seconds`, `mtime_nanos` (`:157-191`, the `INSERT … ON CONFLICT` statement at `:249-260`).
- No encoding stored, no undo history. `mtime` is the buffer's `saved_mtime`: the on-disk file's mtime at the last read/save.
- `Editor` implements `SerializableItem` (`crates/editor/src/items.rs:1253-1546`). `serialize` (`:1462-1534`) takes a buffer snapshot and writes in the background: `contents` = the whole text **only if** the setting allows it and the buffer is dirty; if not dirty, `contents = NULL` (reopen from disk).
- The mode `BufferSerialization::All | NonDirtyBuffers` comes from `session.restore_unsaved_buffers` (`crates/editor/src/editor.rs:772-785`). With `NonDirtyBuffers`, `serialize(closing = true)` returns `None`, meaning hot exit is impossible and a prompt is needed on close.

### 6.2 When it writes

- **On every edit**, throttled: `should_serialize` returns true for `EditorEvent::Saved | DirtyChanged | BufferEdited | FileHandleChanged` (`items.rs:1536-1545`). The workspace receives the item's event and pushes the item into a channel (`crates/workspace/src/item.rs:875-879`, `enqueue_item_serialization`, `workspace.rs:8063-8070`).
- `Workspace::serialize_items` (`workspace.rs:8025-8061`) reads the channel in chunks (at most `CHUNK_SIZE = 200` items), dedupes by `item_id`, serializes each item in the background, then sleeps **`SERIALIZATION_THROTTLE_TIME = 200 ms`** (`workspace.rs:175`). This is a throttle (the first write is immediate, then at most one per 200 ms), not a debounce. Each write is the buffer's **whole** text.
- **At quit through the `Quit` action** (`crates/zed/src/zed.rs:1754-1805`): an optional `confirm_quit` prompt (default false), then `prepare_windows_to_quit` calls `prepare_to_close(CloseIntent::Quit)` for each window, **active window first** (`:1768-1772`; `workspace.rs:12075-12110`). In `save_all_internal(SaveIntent::Close, allow_hot_exit_serialization)` (`workspace.rs:3970-4062`): every dirty item is `serialize(closing = true)`d and awaited; an item that cannot be serialized (not an editor, or `restore_unsaved_buffers` is off, or the DB write failed) goes into the remaining list, and then it asks: several files → *"Do you want to save all changes in the following files?"* with **Save all / Discard all / Cancel**; one file → a per-file save prompt. Cancel in any window cancels the quit; windows already prepared get their serialization flushed (`:12100-12110`). Only when all is done is `cx.quit()` called.
- `cx.on_app_quit(flush_windows_serialization_on_quit)` (`workspace.rs:995`, `:12183-12214`) flushes every item and workspace state of every window. This function runs inside `App::shutdown`, bounded by GPUI's **`SHUTDOWN_TIMEOUT = 200 ms`** (`crates/gpui/src/app.rs:80`, `:1271-1313`).
- **When closing one window** (`prepare_to_close`, `workspace.rs:3733-3864`): hot exit is allowed only when the window can be "found again": it is a Quit, or it is the last window and closing the last window makes the app quit, or the workspace has at least one visible worktree (reopening the folder shows it) (`:3829-3846`). A window that has only untitled buffers, no folder, closed mid-way → asks to save, so that no buffer is abandoned in the DB. If it closes (not a Quit, not the last window), the workspace is removed from the session (`remove_from_session`, `:3852-3859`), but the `editors` rows remain, so reopening that folder still shows the unsaved content.

### 6.3 System-initiated quit (Dock Quit, Log Out)

GPUI macOS only implements `applicationWillTerminate:` (`crates/gpui_macos/src/platform.rs:90-92`, `:1391-1399`), not `applicationShouldTerminate:`, so it cannot veto. Dock Quit/Log Out sends `terminate:` → `applicationWillTerminate:` → `on_quit` → `App::shutdown` → only the `on_app_quit` hooks within 200 ms. Zed's `Quit` action and `prepare_to_close` **do not run**, so there is no prompt. Hot exit is still correct because dirty content was already being written continuously (200 ms throttle) and the final flush runs in `on_app_quit`. Conversely, with `restore_unsaved_buffers: false`, Dock Quit loses unsaved changes without asking.

### 6.4 Restore and files changed on disk

- `Editor::deserialize` (`items.rs:1273-1460`) reads the `editors` row. `restore_unsaved_buffers = false` → drop `contents`, `language`, `mtime` (`:1286-1299`).
- With `abs_path` + `contents`: opens the buffer from disk through the project (`open_path`, or `open_local_buffer` for a file outside the worktree), then `restore_serialized_buffer_contents` (`:2342-2357`): if there is an mtime it calls `did_reload` to set the buffer's `saved_mtime` **to the saved mtime** (not the current mtime), then `set_text(contents)` and removes that transaction from the undo stack (so Undo does not go back to the on-disk version).
- **File changed on disk**: the on-disk mtime is newer than `saved_mtime` and the buffer has unsaved changes → `Buffer::has_conflict()` = true (`crates/language/src/buffer.rs:2556-2571`). The tab gets a conflict indicator color (`crates/workspace/src/pane.rs:5094`). On save, `Pane::save_item` shows the modal *"This file has changed on disk since you started editing it. Do you want to overwrite it?"* with **Overwrite / Discard Edits / Cancel** (`pane.rs:2263`, `:2330-2390`).
- **File deleted**: `open_path` of a file that no longer exists creates an empty buffer with `DiskState::New` (`crates/project/src/buffer_store.rs:728-745`); `contents` is set in so the buffer is dirty, `has_conflict` = false with `New`, and saving **recreates the file without asking**. (The prompt *"has been deleted on disk… recreate it?"* at `pane.rs:2265` is only for `DiskState::Deleted`, i.e. a file deleted while it was open.)
- Untitled buffer (`abs_path = NULL`, has `contents`): creates a new buffer, `set_text` to get the dirty flag, restores the language by name (`items.rs:1313-1364`).
- Garbage cleanup: when loading a workspace, `SerializableItem::cleanup` deletes `editors` rows that no longer belong to any loaded item (`workspace::delete_unloaded_items`, `crates/workspace/src/persistence.rs:2764-2790`). Closing a dirty tab with "Discard" does not delete the row immediately; the row is gone at the next load.

### 6.5 Related settings

- `session.restore_unsaved_buffers` (default `true`, `assets/settings/default.json:2763`; documented in `crates/settings_content/src/project.rs:490-497`): equivalent to turning hot exit on. There is no `onExitAndWindowClose`-style value; the "close window" rule in §6.2 is fixed.
- `restore_on_startup` (`last_session` default | `last_workspace` | `empty_tab` | `launchpad`, `default.json:166-171`): chooses which workspace to reopen (`crates/zed/src/main.rs:1596-1660`). There is no exception for a workspace with unsaved buffers: if it is not reopened, the content stays in the DB until the user reopens that folder.
- `on_last_window_closed` (`platform_default` | `quit_app`, `default.json:233-236`): on macOS decides whether closing the last window quits the app (`zed.rs:336-358`), and therefore whether the last window gets hot exit when closed (`closing_last_window_quits_app`, `crates/workspace/src/workspace_settings.rs:53-62`).
- `confirm_quit` (default false): asks "Are you sure you want to quit?" before Quit.

## 7. Similarities and differences

| Topic | VS Code | Zed (b5cd310) |
|---|---|---|
| On/off | `files.hotExit`: `off` / `onExit` (default) / `onExitAndWindowClose` | `session.restore_unsaved_buffers` true/false |
| When it writes | debounce 1000 ms (2000 ms if auto save is short) after the last change | throttle 200 ms; the first write is immediate |
| Store | one file per working copy in `Backups/<ws>/<scheme>/<hash>` | one row in the SQLite `editors` table |
| Safe write | temp `.vsctmp` + rename | SQLite transaction |
| Meta | URI, typeId, mtime, ctime, size, etag, orphaned | path, language, mtime |
| Quit (Cmd+Q) | no prompt if everything can be backed up | no prompt if everything can be serialized; active window first |
| Close window | macOS: asks (except scratchpads); `onExitAndWindowClose`: backs up | backs up if it has a folder or is the last window and the app quits; otherwise asks |
| Backup failure at quit | error dialog: OK / Quit Anyway | the item falls into the save prompt |
| Slow backup | progress dialog after 800 ms, Cancel → save prompt | waits (no dialog) |
| System-initiated quit | Electron `before-quit`, can still veto | only `on_app_quit`, 200 ms, no veto |
| Window restore | empty windows with backups always open; folder windows follow `restoreWindows` | follows `restore_on_startup`; the rest wait for the folder to be reopened |
| File changed on disk | detected on save: Compare / Overwrite notification | tab shows a conflict at once; on save a modal Overwrite / Discard Edits / Cancel |
| File deleted | save silently recreates | save silently recreates |

## 8. What Lucerna needs to watch

1. **Write backups continuously; do not rely on quit time.** GPUI's `on_app_quit` cannot veto and has only `SHUTDOWN_TIMEOUT = 200 ms` (`gpui/src/app.rs:80`); Dock Quit and Log Out go straight through `NSApp terminate:` → `applicationWillTerminate:`, not through Lucerna's `Quit` action. So the backup must be nearly current before quitting: a VS Code-style debounce (1000 ms) or a Zed-style throttle (200 ms) on each change, written on the background executor. The `on_app_quit` hook only flushes what is still pending, writes synchronously, and accepts that it may be cut off.
2. **Follow VS Code for behavior** (`files.hotExit` with three values, default `onExit`; Cmd+Q does not ask; closing a window on macOS asks; `onExitAndWindowClose` backs up when closing a window with a folder). Lucerna's `Quit` action does this across all windows *before* `cx.quit()`, active window first, like Zed; only when a backup fails does it ask (OK / Quit Anyway), and Cancel cancels the whole quit.
3. **One process, many windows**: a backup folder per workspace, keyed by the same path hash that `workspace_state.rs::state_path` already uses (SHA-256 of the canonical path). Suggested `<data_dir>/backups/<sha256 of folder>/<sha256 of file path>` and a separate folder for windows with no folder/untitled. Each window only writes/deletes in its own folder, so no locking between windows is needed; but two windows opening the same folder (if Lucerna allows it) would collide, so keep the rule "an already open folder focuses that window".
4. **File format**: a JSON header line (path, `mtime`, `size`, optionally the encoding/line ending/BOM that Lucerna keeps) and then the content, written with the existing `write_atomic` (temp + rename). Do not store backups in the workspace's `state.json`: that file is rewritten even on scrolling alone, while a backup can be large and written on every keystroke.
5. **Restore**: when opening a file that has a backup, load the backup instead of the disk and mark it dirty, keeping the saved `mtime` as the "mtime at read time". Skip the step that makes undo go back to the on-disk version (like Zed). A backup for a file that is not open in any tab opens a tab by itself (VS Code opens it pinned, without taking focus). A window with no folder that has a backup is always reopened, like VS Code; a window with a folder follows `window.restoreWindows`, and the backup is kept until that folder is reopened.
6. **File changed on disk while the app was off**: should do slightly better than both references, for example compare mtime/size right at restore and put the tab into a conflict state (as Zed shows a color), and on save use the conflict flow Lucerna already has (following VS Code: Compare / Overwrite). Deleted file: both references silently recreate it on save; Lucerna should at least show the tab as "deleted".
7. **Delete the backup** as soon as it is no longer dirty (save, revert, Don't Save when closing a tab) and when the tab is closed; at startup clean up empty backup folders. Do not delete the unrestored backups of a workspace that has not been reopened.
8. **Auto save** (if Lucerna has it): at quit, really save the files that can be auto saved, and hot exit only handles the rest, like VS Code. Test the quit flow with `simulate_prompt_answer` and re-check the Dock Quit / Log Out path by hand, because `TestPlatform` does not simulate `applicationWillTerminate:`.
